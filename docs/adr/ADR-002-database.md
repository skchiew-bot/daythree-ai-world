# ADR-002: Database

## Context

Spec §6/§8 name PostgreSQL 16+ with pgvector as the core state store for 11 tables
covering tenants, users, agents/agent versions, model policies, missions, tasks, runtime
checkpoints, artifacts, audit events, and model invocations. The database is the system's
source of truth (spec §4 rule 1) — every other component (Redis, object storage) is either
a cache/queue or a blob store, never authoritative for state.

## Options Considered

1. **PostgreSQL 16 (asyncpg driver) everywhere**, including for automated tests.
2. PostgreSQL in production/dev, **SQLite substituted for automated tests** (faster, no
   Docker dependency).
3. A document store (MongoDB) for flexibility on `agent_versions.tool_policy` /
   `settings` / `budget_policy` JSON blobs.

## Decision

PostgreSQL 16 everywhere, with **JSONB** columns for the genuinely schema-flexible fields
(`tool_policy`, `memory_policy`, `settings`, `budget_policy`, `fallback_config`,
`retry_policy`, `payload`, `state`). Automated tests that need a real database use
**testcontainers-python** to spin up a real, throwaway Postgres 16 container — SQLite is
never substituted anywhere, including in tests.

## Rationale

- pgvector is listed as a Phase 0 dependency for future (Phase 1+) semantic search over
  agent memory/knowledge; no Phase 0 table actually stores a vector column yet, but
  starting on Postgres from day one avoids a migration-engine swap later.
- SQLite lacks native JSONB, `ON CONFLICT DO NOTHING`-style upsert semantics identical to
  Postgres, and — critically for spec §14 — the exact `SAVEPOINT` (nested transaction)
  behavior `artifact_service.service.commit_artifact` relies on to reconcile a unique-
  constraint race without rolling back the caller's whole transaction. Testing against
  SQLite would validate a different set of guarantees than production actually has,
  which is a worse failure mode than "tests need Docker."
- Explicit naming convention on `Base.metadata` (`packages/common/db/base.py`) makes
  Alembic-autogenerated constraint names stable and predictable across environments.

## Consequences

- **Every timestamp column is explicitly `DateTime(timezone=True)`** (a module-level
  `TZDateTime` alias in `packages/common/db/models.py`), not the bare
  `Mapped[datetime]` default. This was *not* how the schema first shipped: CI's first
  real run against a live Postgres caught `asyncpg.exceptions.DataError: can't
  subtract offset-naive and offset-aware datetimes` on the very first `audit_events`
  insert, because SQLAlchemy maps an untyped `Mapped[datetime]` to `TIMESTAMP WITHOUT
  TIME ZONE` on Postgres while the rest of the app (`contracts.events` in particular)
  produces timezone-aware `datetime.now(timezone.utc)` values everywhere. No unit test
  could have caught this — it only manifests once a real asyncpg codec is involved.
- `docker-compose.yml` currently runs the plain `postgres:16-alpine` image, **not**
  `pgvector/pgvector:pg16` — since no Phase 0 table has a vector column, the extension
  isn't installed yet. Swapping the compose image and running `CREATE EXTENSION
  vector;` in a migration is the concrete Phase 1 follow-up when a vector column is
  actually needed; tracked here rather than left as a silent gap.
- Every integration test requires Docker; there is no fast, DB-free approximation. This
  is a deliberate trade documented in the top-level `README.md` and this build's
  `PHASE_0_COMPLETION_REPORT.md` — tests that need Postgres are skipped (not faked) when
  Docker is unavailable.
- `missions.assigned_agent_id` and `artifacts.logical_output_slot` were added beyond
  spec §8's literal table definitions — see the docstring at the top of
  `packages/common/db/models.py` for the exact justification for each.
- The initial Alembic migration (`0001_initial_schema.py`) was authored using
  `Base.metadata.create_all`/`drop_all` rather than hand-written `op.create_table(...)`
  calls, because it was written without a live Postgres connection available (Docker
  Desktop was off in the build environment) — see that file's docstring. Any *future*
  schema change should use a normal `alembic revision --autogenerate` against a running
  Postgres, which will correctly diff against this baseline.

## Rollback Path

None needed at the storage-engine level (Postgres is not being replaced). If pgvector
specifically turns out to be unnecessary, drop the extension requirement from
`infrastructure/docker/` — no application code currently depends on it.
